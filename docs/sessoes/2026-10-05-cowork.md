- `[ficheiro]` A `generate-guioes-weekly` tem o mesmo `papelDoPedido` à entrada (l.23–46).
  Logo a inferência do Code está certa: a chamada do GitHub chega com `role: service_role`.

- `[mcp]` Estado publicado: `generate-guiao-questions` v3 e `generate-guioes-weekly` v5, ambas
  `verify_jwt: true`, publicadas a 28/09.
- `[logs]` 05/10, 14:28:11–14:28:14: **4 chamadas** à `generate-guiao-questions`, todas 403,
  vindas de `supabase-js/2.117.2` dentro do runtime das Edge Functions, com `apikey` de
  prefixo **`sb_secret_`** e cabeçalho `sb_api_key_compatibility: minted`. Região us-west-1.
- `[logs]` As chamadas do GitHub (curl) à `archive-weekly` e à `generate-guioes-weekly`
  (200) **não** levam chave `sb_secret_` — coerente com a chave antiga JWT no segredo do
  GitHub.
- `[docs]` Com `verify_jwt` ligado, a plataforma rejeita com **401** um `Authorization` que
  não seja JWT, antes de o código correr. Chaves publishable/secret não são JWT.
  Fontes: https://supabase.com/docs/guides/functions/auth-headers ·
  https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys

**Conclusão, com o grau de certeza de cada parte:**

- **Verificado:** a chamada interna sai com uma chave `sb_secret_`, não com a JWT antiga.
  A primeira metade da hipótese do Code confirma-se — pelos logs, sem ler o valor da chave.
- **Não verificado — o mecanismo:** o 403 traz o corpo do nosso código, portanto a plataforma
  deixou passar o pedido apesar do `verify_jwt: true`. O cabeçalho `minted` sugere que a
  plataforma gerou um JWT de compatibilidade a partir da chave secreta; esse JWT não tem
  `role: service_role` (ou não chega no `Authorization`). Isto é leitura dos cabeçalhos, não
  teste. Para fechar: registar na `generate-guiao-questions` o número de partes do token e o
  `role` do payload (nunca o token).
- A explicação do Code ("sem três partes → `null`") **não bate certo sozinha** com o
  `verify_jwt: true`: um token sem três partes teria dado 401 da plataforma, não o nosso 403.

### 4.5 A correcção proposta (reencaminhar o `Authorization`)

- Funciona com o que se viu: o `Authorization` que entra vem do GitHub e tem
  `role: service_role`.
- **Mas fica preso às chaves antigas.** Se as chaves JWT antigas forem desligadas no projecto,
  a chamada do GitHub deixa de passar o `verify_jwt` e tudo pára. A alternativa de fundo
  (`verify_jwt = false` + autorização no código pelo `apikey`, ou o SDK `@supabase/server`)
  é a que a documentação indica para as chaves novas — não é para 06/10, fica registada.
- **Fazer primeiro o diagnóstico de 4.4**, depois a correcção. Corrigir sem saber o mecanismo
